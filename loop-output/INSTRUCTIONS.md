## 3. Алгоритм одной итерации

```
1. ПРОЧИТАТЬ этот файл (INSTRUCTIONS.md) целиком
2. ПРОЧИТАТЬ loop-output/progress.md → найти текущую задачу (первая незавершённая)
3. ПРОЧИТАТЬ описание задачи в ПЛАН_РАЗРАБОТКИ.md (секция с Задача/Цель/Итог)
4. ВЫПОЛНИТЬ задачу:
   a. Написать/изменить код
   b. Если backend → запустить тесты (см. §5)
   c. Если frontend → запустить проверку типов + линтер (см. §5)
   d. Убедиться, что Итог задачи выполнен
5. КОММИТ в ветку auto/ibra-dev с описанием что сделано
6. ОБНОВИТЬ progress.md → пометить задачу ✅, записать дату/время
7. ОБНОВИТЬ ПЛАН_РАЗРАБОТКИ.md → поставить [x] у выполненного шага
8. Если всё по плану → СТОП (одна задача за итерацию)
   Если задача не завершена (тесты красные / блокер) → записать в progress.md причину, СТОП
```

## 4. Правила

### 4.1 Общие
- **Ровно одна задача за итерацию.** Не перескакивай, не делай две.
- **Коммит после каждого изменения.** Коммит-сообщение: `[Phase X.Y] краткое описание`. Пример: `[Phase 0.1] init repo structure`.
- **Ветка:** `auto/ibra-dev`. Создай при первой итерации если не существует.
- **Дата/время:** бери командой `date` (PowerShell: `Get-Date`), записывай в progress.md.
- **Состояние — только в файлах.** Не полагайся на память между итерациями.

### 4.2 Код
- Backend: структура `backend/app/` (models/, routers/, services/, schemas/, core/).
- Frontend: структура `frontend/src/` (components/, pages/, ui/, hooks/, api/, types/).
- Дизайн-токены и компоненты UI: `frontend/src/ui/` — по спеке из ДИЗАЙН_СИСТЕМА.md.
- Каждая модель = своя миграция Alembic.
- Pydantic-схемы для всех входов/выходов API.
- Backend-проверка прав на каждой мутации (require_role).
- Все денежные поля: `Decimal` / `numeric`, не `float`.
- Комментарии в коде — только если WHY неочевидно.

### 4.3 Тесты
- Задача считается закрытой **только при зелёных тестах** (или при отсутствии тестов, если шаг — чисто инфраструктурный, напр. 0.1).
- Тесты пишутся для: прав доступа, расчёта прибыли, контроля остатков, автонумерации.

### 4.4 Git
- Не делай force-push.
- Не трогай main/master.
- Коммить конкретные файлы (не `git add -A`).

## 5. Команды проверки

### Backend
```bash
cd backend
# Установка зависимостей (первый раз)
pip install -r requirements.txt

# Тесты
python -m pytest tests/ -v

# Линтер
python -m ruff check .

# Типы (если настроен mypy)
python -m mypy app/ --ignore-missing-imports
```

### Frontend
```bash
cd frontend
# Установка (первый раз)
npm install

# Проверка типов
npx tsc --noEmit

# Линтер
npx eslint src/ --ext .ts,.tsx

# Dev-сервер (для визуальной проверки)
npm run dev
```

### Docker
```bash
# Поднять всё
docker compose up -d

# Только БД
docker compose up db -d
```

> **Адаптируй команды** если при выполнении выясняется, что структура/конфиг отличается (напр. pyproject.toml вместо requirements.txt). Обнови этот файл если меняешь команды.

## 7. Фаза HARDEN+ANALYZE

Когда **все задачи плана** (Фазы 0–15) выполнены, переходи в режим усиления:

### HARDEN (укрепление)
1. Пройди все экраны и проверь edge cases (пустые списки, длинные названия, нулевые суммы, отрицательные курсы).
2. Проверь все роли (админ/менеджер/наблюдатель) на каждом экране.
3. Проверь адаптив (375px, 768px, 1024px, 1440px).
4. Запусти полный набор тестов. Починь красные.
5. Каждый фикс = отдельный коммит `[HARDEN] описание`.

### ANALYZE (отчёт)
Веди два файла:

**loop-output/HARDEN_REPORT.md** — что проверено, что починено:
```markdown
# HARDEN Report

| # | Проверка | Результат | Фикс (коммит) |
|---|----------|-----------|---------------|
| 1 | Пустой список заказов | OK | — |
| 2 | Наблюдатель видит кнопку удаления | БАГ | abc1234 |
```

**loop-output/FINAL_REPORT.md** — итоговый отчёт:
```markdown
# Final Report — Ibra Order System

## Статус: ГОТОВО / В РАБОТЕ
## Покрытие плана: X/Y задач (Z%)
## Тесты: X passed, Y failed
## Открытые проблемы: ...
```
