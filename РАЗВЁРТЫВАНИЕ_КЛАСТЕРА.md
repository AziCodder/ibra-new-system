# Развёртывание кластера: два сервера, два S3, домен

Пошаговая инструкция от «серверы куплены» до «работает на
https://flow.cargo-ibragim.ru». Каждый шаг заканчивается проверкой — если
она не прошла, дальше идти нельзя.

---

## 0. Что заказать

Серверы у **разных** провайдеров (HostKey и AdminVPS) — это осознанно:
авария одного провайдера не должна класть обе машины.

**Оба сервера одинаковые:**

| Параметр | Значение | Почему так |
|---|---|---|
| CPU | 2 ядра | Приложение лёгкое; пик — pg_dump и сборка образов |
| RAM | 4 ГБ | PostgreSQL + 3 контейнера + сборка фронтенда |
| Диск | 60 ГБ SSD | База, образы, бэкапы «на перевалке» |
| ОС | Ubuntu 22.04 или 24.04 LTS | Под неё написаны скрипты |
| Сеть | Публичный IPv4, ≥ 100 Мбит | IP должен быть постоянным |

**О чём спросить провайдера до оплаты:**

1. IP выделяется постоянный, при перезагрузке не меняется?
2. Открыт ли UDP-порт 51820 (туннель между серверами) — он не должен быть
   зарезан фильтрами.
3. Есть ли API для управления DNS/IP (пригодится, но не обязателен).

Размещать серверы лучше в **одном городе**: синхронная репликация ждёт
второй сервер на каждой записи. Между двумя площадками в Москве это +2–5 мс,
между Москвой и Амстердамом — +40–60 мс на КАЖДУЮ операцию записи, и это
будет заметно на массовых действиях.

**Хранилища:** бакет в HostKey S3 (основной) и бакет в Storj (зеркало).
Ключи доступа с правами на чтение/запись/удаление в своём бакете.

## 1. Базовая подготовка (на обоих серверах)

```bash
apt update && apt upgrade -y
apt install -y docker.io docker-compose-plugin git ufw
systemctl enable --now docker
```

Фаервол — открыт только необходимый минимум:

```bash
ufw allow 22/tcp
ufw allow 80/tcp
ufw allow 443/tcp
ufw allow 51820/udp
ufw enable
```

Порт PostgreSQL наружу **не открывается**: реплика ходит внутри туннеля.

**Проверка:** `docker run --rm hello-world` отрабатывает без ошибок.

---

## 2. Туннель между серверами

Серверы у разных провайдеров, общей приватной сети между ними нет. Весь
обмен — поток репликации (это все ваши данные) и проверки живости — пойдёт
через открытый интернет, поэтому поднимаем шифрованный туннель. Заодно у
каждого узла появляется постоянный внутренний адрес: **A = 10.8.0.1**,
**B = 10.8.0.2**.

На сервере A:
```bash
sudo ./ops/wireguard/setup-wireguard.sh A <публичный-IP-B>
```
Скрипт напечатает публичный ключ. На сервере B:
```bash
sudo PEER_PUBLIC_KEY=<ключ-A> ./ops/wireguard/setup-wireguard.sh B <публичный-IP-A>
```
Вернуться на A и повторить с ключом B.

**Проверка:** `ping 10.8.0.2` с A и `ping 10.8.0.1` с B отвечают.

## 3. Выкладка приложения (на обоих серверах)

```bash
git clone <репозиторий> /opt/ibra && cd /opt/ibra
cp backend/.env.production.example .env
```

Заполнить `.env`. Одинаково на обоих серверах:

- `SESSION_SECRET` — 64 случайных символа (`openssl rand -hex 32`);
- `POSTGRES_PASSWORD` — одинаковый на обоих;
- `PUBLIC_BASE_URL=https://flow.cargo-ibragim.ru`,
  `CORS_ORIGINS=https://flow.cargo-ibragim.ru`,
  `TRUSTED_HOSTS=flow.cargo-ibragim.ru`;
- `STORAGE_BACKEND=s3` и реквизиты обоих бакетов;
- `TELEGRAM_BOT_TOKEN`, `ALERT_CHAT_ID`.

Различается только три строки:

| Переменная | Сервер A | Сервер B |
|---|---|---|
| `NODE_NAME` | `A` | `B` |
| `NODE_PUBLIC_IP` | публичный IP A | публичный IP B |
| `PEER_URL` | `http://10.8.0.2/api/cluster/ping` | `http://10.8.0.1/api/cluster/ping` |

`FAILOVER_ENABLED` пока оставить `false` — включим на шаге 7, после учений.

Запуск:
```bash
docker compose -f docker-compose.prod.yml up -d --build
docker compose -f docker-compose.prod.yml exec backend alembic upgrade head
```

Администратор создаётся только на сервере A (на B данные приедут репликой):
```bash
docker compose -f docker-compose.prod.yml exec backend \
  python -m app.scripts.create_admin admin '<пароль>' 'Администратор'
```

**Проверка:** `curl -s localhost:8080/` отдаёт страницу на обоих серверах.

## 4. Хранилища S3

В `.env` (оба сервера):
```
STORAGE_BACKEND=s3
S3_PRIMARY_ENDPOINT=https://<эндпоинт HostKey S3>
S3_PRIMARY_BUCKET=ibra-files
S3_PRIMARY_ACCESS_KEY=...
S3_PRIMARY_SECRET_KEY=...
S3_MIRROR_ENDPOINT=https://gateway.storjshare.io
S3_MIRROR_BUCKET=ibra-files
S3_MIRROR_ACCESS_KEY=...
S3_MIRROR_SECRET_KEY=...
```

Проверка связи с обоими бакетами:
```bash
docker compose -f docker-compose.prod.yml exec backend \
  python -m app.scripts.check_s3
```

Перенос файлов со старого диска (только на сервере A, один раз):
```bash
docker compose -f docker-compose.prod.yml exec backend \
  python -m app.scripts.migrate_files_to_s3 --dry-run   # посмотреть
docker compose -f docker-compose.prod.yml exec backend \
  python -m app.scripts.migrate_files_to_s3             # перенести
```

**Проверка:** загрузить файл к заказу через интерфейс, затем убедиться, что
объект появился в обоих бакетах (вкладка «Состояние системы» показывает оба
хранилища как работающие).

## 5. Репликация базы

На сервере A:
```bash
sudo REPLICATION_PASSWORD='<пароль>' PEER_IP=10.8.0.2 ./ops/pg/setup-primary.sh
docker compose -f docker-compose.prod.yml restart db
```

На сервере B (**сотрёт локальную базу B и нальёт копию с A**):
```bash
sudo REPLICATION_PASSWORD='<тот же пароль>' PRIMARY_IP=10.8.0.1 ./ops/pg/setup-standby.sh
```

**Проверка на A:**
```bash
docker compose -f docker-compose.prod.yml exec db \
  psql -U postgres -c 'SELECT application_name, state, sync_state FROM pg_stat_replication;'
```
Должна быть строка `standby | streaming | sync`. Значение `sync` —
подтверждение того, что запись действительно ждёт второй сервер.

**Проверка на B:** `SELECT pg_is_in_recovery();` возвращает `t`.

## 6. Домен и HTTPS

Домен `cargo-ibragim.ru` обслуживается в reg.ru. Нужна запись
`flow` → IP сервера A, с минимально возможным TTL.

Сертификат на каждом сервере отдельно:
```bash
# на A (домен указывает на A)
sudo EMAIL=<почта> ./ops/edge/issue-cert.sh
# затем временно перевести домен на B и повторить там же
```

Если сертификат куплен, а не Let's Encrypt: положить `fullchain.pem` и
`privkey.pem` в том `certs` по пути
`/etc/letsencrypt/live/flow.cargo-ibragim.ru/` на обоих серверах.
Сертификат должен покрывать **flow.cargo-ibragim.ru** — сертификат на
`cargo-ibragim.ru` без wildcard для поддомена не подойдёт.

**Проверка:** `curl -sI https://flow.cargo-ibragim.ru` отвечает `200`,
браузер показывает замок, http перебрасывает на https.

## 7. Включение автоперехвата и учения

Только после того, как всё выше проверено.

```
FAILOVER_ENABLED=true
DNS_PROVIDER=regru        # или cloudflare, если зона делегирована туда
REGRU_LOGIN=...
REGRU_PASSWORD=...
```
```bash
docker compose -f docker-compose.prod.yml up -d worker
```

**Учения** (проводить в нерабочее время, заранее сняв ручной бэкап):

1. Снять бэкап через админку, назвать «перед учениями».
2. На сервере A: `docker compose -f docker-compose.prod.yml stop`.
3. Засечь время. Ожидаемое поведение: через ~2 минуты молчания B повышает
   свою базу до главной и переводит домен на себя; в Telegram приходит
   уведомление.
4. Проверить: сайт открывается, создание заказа проходит, файл загружается.
5. Вернуть A в строй **только как резерв**:
   ```bash
   sudo REPLICATION_PASSWORD='...' PRIMARY_IP=10.8.0.2 ./ops/pg/rejoin-as-standby.sh
   ```
6. Записать фактическое время переключения — это и есть реальный простой,
   а не тот, который «должен быть».

## Что нужно знать про сроки переключения

Серверы у разных провайдеров, поэтому «плавающего» IP между ними не
существует — переносить адрес умеет только провайдер внутри своей сети.
Переключение делается через DNS, а DNS живёт в кэшах: даже при TTL 60 секунд
часть посетителей, провайдерских резолверов и браузеров ещё какое-то время
будет стучаться на старый адрес.

Честная оценка простоя при аварии:

| Этап | Время |
|---|---|
| Обнаружение (4 проверки по 30 c) | ~2 мин |
| Повышение базы и смена DNS-записи | секунды |
| Расход кэшей DNS у клиентов | 1–15 мин (TTL reg.ru обычно от 300 c) |

Если такой простой неприемлем, есть два пути:

1. **Делегировать зону в Cloudflare** — TTL 60 секунд и предсказуемое
   распространение. Бесплатно. Простой сокращается примерно до 3–5 минут.
2. **Взять оба сервера у одного провайдера** и использовать переносимый IP —
   тогда переключение занимает секунды, но исчезает защита от аварии
   самого провайдера. Это размен, а не улучшение.

## Порядок при плановых работах

Обновление без простоя невозможно (узел один), но можно сделать его
коротким и предсказуемым:

1. Снять ручной бэкап через админку.
2. Обновить резерв (B): `git pull && docker compose ... up -d --build`.
3. Убедиться, что репликация не отвалилась.
4. Переключиться на B вручную (`promote.sh` + смена DNS).
5. Обновить A, вернуть его резервом.

Так система переживает обновление в худшем случае с одним коротким
переключением, а не с падением обоих узлов сразу.
