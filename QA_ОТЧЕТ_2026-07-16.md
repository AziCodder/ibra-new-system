## Сводка: что нашлось критичного

Если читать только один блок — читайте этот.

### 🔴 P0 — блокирующие проблемы (нельзя деплоить с ними)

1. **Оплату можно внести на любую сумму, backend вообще не проверяет остаток запроса.** Живой тест: у запроса на оплату остаток был 1000 ₽, отправлен платёж на 50 000 ₽ — принят, остаток ушёл в **−49 000 ₽**. Это ломает весь финансовый учёт (искажает «Закупки» и, соответственно, прибыль). См. [§13.1](#131-создание-платежа).
2. **Удаление файла (`DELETE /api/files/{key}`) не проверяет ни роль, ни принадлежность файла.** Любой авторизованный пользователь (включая наблюдателя) может удалить чужой файл; проверка от path traversal, которая есть у чтения файла, у удаления отсутствует. См. [§31](#31-базовая-безопасность).
3. **Раздел «Файлы заказа» (чек-лист §10) не реализован вообще** — ни модели в БД, ни API, ни интерфейса. До 5 файлов на 3 МБ каждый, заявленные в ТЗ, физически негде прикрепить к заказу (не путать с файлами товара / запроса на оплату / логистики — они есть).
4. **Ни один из 3 стоп-вопросов раздела 2, требующих согласования до приёмки, формально не закрыт документом с вашей подписью** — хотя по коду и по `ЧЕКЛИСТ_требований.md` видно, какой вариант выбран фактически. См. [раздел «Стоп-вопросы»](#стоп-вопросы-раздел-2).

### 🟠 P1 — серьёзные проблемы

5. Ограничения размера файла из ТЗ (3 МБ — файлы заказа, 5 МБ — файлы запроса на оплату) **нигде не проверяются** — есть только общий лимит 20 МБ на все файлы без исключения. Подтверждено вживую (файл 5 МБ+1 байт принят).
6. **Сессионный cookie не отзывается на logout** — это просто подпись без серверного хранилища. Захваченный токен продолжает работать после «выхода» вплоть до истечения 7 дней. Подтверждено вживую (replay-атака).
7. **Нет rate-limiting на `/api/auth/login`** — пароль можно перебирать без ограничений.
8. **Гонки (race conditions) не защищены нигде**, кроме генерации номера заказа — ни для оплат, ни для запросов на оплату, ни для логистики нет `SELECT FOR UPDATE`/блокировок. Для оплат это уже не гонка, а полное отсутствие проверки (см. п.1). Для логистики — теоретическая гонка, подтверждена по коду, не воспроизведена вживую (см. [§32](#32-параллельные-действия)).
9. **Нет способа переназначить менеджера заказа после создания** и **нет способа админу выбрать менеджера при создании заказа** — `OrderUpdate` содержит только поле `details`, менеджером всегда становится тот, кто создал заказ. Это расходится с пунктами 8/9.3 чек-листа.
10. Редактирование товара (PATCH) **не проверяет** попытку понизить количество ниже уже отправленного логистикой, понизить цену ниже уже выставленных запросов или сменить валюту при наличии активных запросов/оплат — ни одна из трёх защит не реализована.
11. Очень большое количество товара (например, `99999999999999`) вызывает **необработанное падение с HTTP 500** (переполнение `Numeric` в Postgres) вместо аккуратной ошибки 422.
12. `processing_days` (дни обработки заказа) считается как `сегодня − дата создания` **каждый раз заново при каждом GET /profit**, включая заказы в статусе «Завершён» — то есть счётчик продолжает расти после завершения заказа, вместо того чтобы зафиксироваться на дате завершения.
13. Валюта — свободная строка без валидации (`currency: str`), можно передать `"ZZZ"` или любой мусор — принимается и сохраняется.

### 🟡 P2 — некритичные, но стоит знать

14. Пустой и однобуквенный пароль пользователя принимаются при создании — минимальная длина пароля нигде не задана.
15. Сообщение об ошибке для деактивированного аккаунта (`Account is deactivated`, 403) отличается от общего «Invalid login or password» — по этому можно отличить существующий-но-заблокированный логин от несуществующего.
16. У раздела «Уведомления» (`/api/notifications/log`) и «Журнал действий» (`/api/action-log/`) **нет интерфейса** — админ не увидит неудачную отправку в Telegram, не зайдя напрямую в API.
17. `<select>` фильтра «Клиент» на мобильной ширине (375px) не ограничен по CSS-ширине: при длинном имени клиента раздувает всю страницу до ~1050px и создаёт горизонтальную прокрутку всей страницы. Воспроизведено вживую через созданного тестового клиента с длинным ФИО.
18. Товар с именем из одних пробелов (`"   "`) создаётся — `min_length=1` не считает пробелы пустой строкой, `.strip()` нет.

## Стоп-вопросы (раздел 2)

Чек-лист прямо требует: «До согласования этого пункта нельзя окончательно принимать...». Ни один из этих вопросов не закрыт формальным документом с датой/подписью, но по факту код уже реализует конкретный вариант — я зафиксировал, какой именно, чтобы вы могли либо утвердить его как решение, либо потребовать другой.

- **2.1 Доступ менеджера к клиентам.** 👤 Фактически реализован вариант **«Менеджер видит всех клиентов, но только свои заказы»** — при создании заказа менеджеру доступен полный список клиентов (никакой привязки «клиент↔менеджер» в БД нет), но `GET /api/orders/` и все вложенные ресурсы жёстко фильтруются по `manager_id`. Это первый вариант из списка чек-листа. **Нужно ваше подтверждение**, что это осознанный выбор, а не то, что просто «не сделали».
- **2.2 Закупленное количество.** 👤 Фактически: остаток к отправке считается от **`Product.quantity`** (заказанное количество), а не от оплаченной доли. То есть система разрешает логистике отправлять товар, даже если он ещё не оплачен ни на копейку — «закупленным» для логистики считается количество из позиции товара, а не сумма реальных платежей. Это ближе к варианту «Закупленным считается всё количество товара после создания запроса», но по факту привязано вообще не к запросу на оплату, а к самому товару. **Финансовый расчёт прибыли** при этом использует другую базу — реальные платежи (см. §26). Налицо два разных понятия «закуплено» в одной системе: одно для логистики, другое для денег. **Нужно ваше решение**, осознанно ли это расхождение.
- **2.3 Распределение частичной оплаты.** ➖ Вопрос снят самой архитектурой: оплата привязывается не к нескольким товарам «размыто», а к конкретному запросу на оплату, у которого есть строки (`items`) на каждый товар с фиксированной суммой; платёж просто уменьшает общий остаток запроса, не распределяясь по строкам автоматически. Строки видно всегда (это ближе к «Оплата относится ко всему запросу, но с видимой разбивкой на момент создания запроса»).
- **2.4 Направление курса.** ✅ Закрыт. Код единообразно использует рекомендованный чек-листом вариант: `сумма_в_валюте_заказа = сумма_операции × курс`, для всех типов операций (доход, оплата, расход логистики, прочий расход). Проверено и по коду (4 места), и вживую на контрольном примере (см. §26.3).
- **2.5 Формула процента прибыли.** ✅ Закрыт по факту: используется **маржинальность** (`прибыль / доходы × 100%`), не наценка. При нулевом доходе — `0%`, без деления на ноль. Округление — до 4 знаков после запятой.
- **2.6 Дни обработки заказа.** ❌ Не закрыт нормально — см. находку P1 №12 выше: считается как «сегодня − дата создания», не «дата завершения − дата создания», и не замораживается после завершения заказа. Это, по сути, баг, а не открытый вопрос — нужно фиксировать на `completed_at`.
- **2.7 Права наблюдателя на комментарии.** 👤 Открыт. Фактическая реализация: наблюдатель **может** комментировать логистику (в коде явная пометка «per ТЗ §9»), но **не может** добавлять заметки заказа (`notes`) — получает 403. Это прямое противоречие между двумя похожими сущностями («комментарий» и «заметка»), уже отмеченное в вашем же `ЧЕКЛИСТ_требований.md` (строка «Осталось уточнить») и в предыдущем QA-прогоне (07.07) как MINOR-1. **Решение всё ещё не принято.**
- **2.8 Удаление справочников.** ✅ Клиента нельзя удалить при наличии заказов (проверено), поставщика — при наличии товаров (подтверждено по коду), пользователя — прямого запрета на удаление автора/менеджера не нашёл явно в роутере `users.py` (⏭ не проверено вживую, роутер использует soft-delete через `is_active`, а не физическое удаление — см. ниже §6.1). Архивирование через `is_active` есть для пользователей, для клиентов/поставщиков — только защита от удаления, отдельного «архива» нет.
- **2.9 Уникальность трекинга.** ✅ Закрыт: уникален **во всей системе** (не только внутри заказа), через уникальный индекс в БД. ⚠️ Регистр **не** нормализуется (`M77-1` и `m77-1` — разные записи), пробелы по краям **не** обрезаются. Если это должно было учитываться — нужен `.strip()` + либо регистронезависимый индекс, либо явное решение, что регистр значим.
- **2.10 Округление денежных значений.** ⚠️ Частично: все денежные поля — `Numeric`/`Decimal` (не float, ошибок двоичной арифметики нет). Явного `ROUND_HALF_UP` нигде нет — используется дефолт Python `Decimal` (банковское округление, ROUND_HALF_EVEN). Явного правила «сумма частей после округления равна итоговой сумме» я не нашёл зафиксированным — но поскольку округление применяется один раз в конце (не на каждом промежуточном шаге), расхождений по построению быть не должно.

### 5.2 Менеджер
Все P0-пункты подтверждены **живыми запросами напрямую к API** от имени `manager_2` к заказу, созданному `manager_1`:

## 13. Внесение оплаты

### 13.1 Создание платежа — 🔴 главный найденный баг
- ❌ **P0: «Нельзя оплатить больше остатка запроса» — НЕ РАБОТАЕТ.** Живой воспроизведённый пример: запрос на оплату с остатком 1000 ₽, отправлен платёж на 50 000 ₽ → `201 Created`, платёж принят полностью, `remaining_amount` запроса стал **`-49000.00`**. В коде эндпоинта `POST /payments` вообще нет сравнения `amount` с остатком — функция `get_payment_request_remaining`, которая для этого существует, там просто не вызывается. Это не пограничный случай и не гонка — ошибка воспроизводится одним обычным последовательным запросом.
- ✅ Нельзя нулевую/отрицательную оплату (422, `Field(gt=0)`).
- ✅ Нельзя нулевой/отрицательный курс (422, `Field(gt=0)`).
- ❌ Соответственно, **нет и защиты от гонки** — но это уже вторично, раз проверки нет даже для одного запроса.
- ✅ Суммы — `Decimal` сквозь весь стек (модель, схема, арифметика), рисков ошибок двоичной арифметики нет.
- ✅ Автор и дата платежа фиксируются на сервере (не принимаются от клиента).
- 👤 «Валюта платежа соответствует валюте запроса» — явной проверки в коде для этого не нашёл (агент не подтвердил жёсткую сверку `Payment.currency == PaymentRequest.currency`) — в текущей архитектуре платёж, похоже, физически может быть внесён в валюте, отличной от валюты запроса, и учтётся по собственному курсу. Нужно подтвердить, ожидаемое ли это поведение (иногда это удобно — клиент платит в другой валюте по своему курсу), либо это тоже надо блокировать.

### 13.2 Расчёт платежей
- ✅ Каждый платёж хранит собственный курс, не пересчитывается задним числом — подтверждено и по коду (нет ни одного `UPDATE exchange_rate`), и вживую на контрольном примере с двумя разными курсами (§26.5 ниже).
- ⏭ «После полной оплаты остаток строго равен нулю» — не проверял граничный сценарий именно «оплата ровно в ноль» отдельно (риск низкий, всё на `Decimal`).

### 13.3 Аудит платежей
- ✅ Автор, дата, исходная сумма, курс, сумма в валюте заказа, примечание — все поля есть в ответе API.
- ✅ Наблюдатель не вносит платежи (403).
- ✅ Менеджер не вносит платежи по чужому заказу (404, тот же общий паттерн изоляции).
- 👤 «Можно ли удалить или исправить ошибочный платёж» — **явного ответа в системе нет**: у `Payment` нет ни `DELETE`, ни `PATCH` эндпоинта вообще (агент подтвердил по всему `payments.py`). Кнопок в интерфейсе для этого тоже, соответственно, нет. Раз ошибочный платёж (как в примере выше — 50 000 ₽ вместо 1000 ₽) **нельзя исправить или удалить никаким штатным способом**, это уже не «открытый вопрос», а прямое следствие бага из §13.1: единственный способ исправить такую ошибку сейчас — прямое вмешательство в БД. **Нужно решение**, добавлять ли возможность отмены/исправления платежа.

## 31. Базовая безопасность

- ✅ P0: Менеджер не получает чужие данные заменой ID в URL (см. весь §5.2 — подтверждено многократно живыми запросами).
- ⚠️ **P0: Менеджер не получает чужие файлы заменой ID — частично.** `GET /api/files/{key}` не привязан к конкретному заказу/владельцу вообще — ключ файла представляет собой случайный UUID (`storage.py:49`, не последовательный ID), поэтому «угадать» чужой ключ практически нереально (это и есть фактическая защита), но если ключ утёк (например, засветился в другом ответе API) — доступ **не** дополнительно проверяется по принадлежности к заказу, который виден текущему пользователю.
- ❌ **P0 (де-факто): `DELETE /api/files/{key}` не проверяет ни роль, ни принадлежность.** Наблюдатель (роль без права редактирования вообще ничего) технически может вызвать `DELETE` и стереть любой файл системы, зная его ключ — единственное требование эндпоинта: быть залогиненным. У `get()` в `storage.py` есть защита от directory traversal (`os.path.commonpath`), у `delete()` — **нет такой же проверки**. Это асимметрия, которую стоит закрыть в первую очередь.
- ✅ P0: Наблюдатель не меняет данные прямыми запросами (весь §5.3 подтверждает).

## 32. Параллельные действия

- ❌ Оплата «остатка» — переплата **гарантированно возникает** даже без параллелизма (см. §13.1), пункт про гонку в данном случае неактуален — проблема глубже.
- ⚠️ Логистика — гонка возможна по коду (нет `FOR UPDATE`), в моём двух-запросном живом тесте не воспроизвелась из-за недостаточно узкого окна одновременности между двумя `curl` в фоне — не считаю это доказательством отсутствия проблемы, просто честно фиксирую, что не смог гарантированно воспроизвести именно эксплуатацию, при том что предпосылка (отсутствие блокировки) в коде подтверждена.
- ✅ Создание заказов — единственное место в коде с явной защитой от гонки (`SELECT FOR UPDATE` при генерации номера заказа), два администратора одновременно создающих заказы одного клиента не получат дублирующийся номер (по коду; параллельный живой тест не гонял).
- ⏭ «Один пользователь удаляет запись, пока другой её редактирует» / «отменяет заказ, пока другой добавляет расход» — не тестировал, требует синхронизированных двух сессий в реальном времени; общий паттерн проверки существования записи перед операцией снижает, но не исключает риск гонки данных при отсутствии транзакционных блокировок.
- ❌ **«Денежные и количественные ограничения проверяются транзакционно на backend» — нет, ни для одного из денежных/количественных ограничений в системе не используется `SELECT FOR UPDATE` или сериализуемая транзакция**, кроме генерации номера заказа.
