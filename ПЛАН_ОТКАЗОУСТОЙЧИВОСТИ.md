# План отказоустойчивости и резервного копирования

Дата: 2026-08-24 (размещение серверов уточнено 2026-08-25).
Домен: **https://flow.cargo-ibragim.ru/**
Инфраструктура: **два сервера у разных провайдеров — Нидерланды (A) и
Финляндия (B)** + два независимых S3 (**HostKey S3** и **Storj**).

Решения, зафиксированные с заказчиком:

| Вопрос | Решение |
|---|---|
| Режим кластера | **актив-пассив с автопереключением** |
| Размещение | **A — Нидерланды, B — Финляндия**, разные провайдеры |
| Реплика PostgreSQL | **асинхронная** — расстояние между площадками делает синхронную слишком дорогой (+30 мс на каждую запись) |
| Потеря при аварии | не ноль: теряется то, что не доехало до резерва (обычно доли секунды работы) |
| S3 | **два разных провайдера**: HostKey S3 (основной) + Storj (зеркало) |
| Бэкапы | часовые — хранятся 7 дней; суточные — вечно |

Асинхронный режим — сознательный размен скорости на строгость: он выбран
после того, как площадки развели по разным странам. Если серверы когда-нибудь
окажутся в одном городе, `SYNC_REPLICATION=true` вернёт нулевую потерю почти
бесплатно.

## 1. Целевая топология

```
                       flow.cargo-ibragim.ru
                                |
                       [ переносимый IP / DNS ]
                                |
              +-----------------+-----------------+
              v                                   v
      +---------------+  асинхронная       +---------------+
      |  СЕРВЕР A     |   репликация       |  СЕРВЕР B     |
      |  (активный)   | -----------------> |  (резерв)     |
      |               |                    |               |
      | nginx + TLS   |   watchdog <-----> | nginx + TLS   |
      | backend       |   (взаимный        | backend       |
      | frontend      |    контроль)       | frontend      |
      | PG primary    |                    | PG standby    |
      | worker (jobs) |                    | worker (спит) |
      +-------+-------+                    +-------+-------+
              |                                    |
              +----------> S3 #1 (HostKey) <-------+
                                |  зеркалирование + сверка
                                v
                           S3 #2 (Storj)
```

Ключевые принципы:

1. **Файлы не лежат на дисках серверов.** Любая загрузка идёт сразу в оба S3;
   сервер — это только вычисления. Падение сервера не теряет ни одного файла.
2. **Один источник правды для БД.** Пишет только активный узел. Резерв —
   асинхронная реплика: изменения уезжают на второй сервер непрерывно, но
   клиент не ждёт их доставки. Отсюда окно потери — то, что не доехало в
   момент аварии. Размер окна виден в админке, за порогом следит воркер.
3. **Фоновые задачи (бэкапы, сверка S3) выполняет только активный узел.**
   Определение «я активный» — по самой БД: `pg_is_in_recovery() = false`.
   Отдельный координатор не нужен, двойной запуск невозможен по построению.
4. **Всё состояние видно в админке** — вкладки «Кластер», «Бэкапы»,
   «Хранилище», расширенное «Состояние системы».

## 3. Шаги работ

### Шаг 2.1 — S3-хранилище с двойной записью *(код)*
* `S3Storage`: запись в оба бакета, чтение — из основного с автоматическим
  падением на зеркало.
* Таблица `stored_files`: ключ, имя, размер, SHA-256, статус в каждом бакете.
  SHA-256 считаем сами — сверка по нему, а не по ETag (у Storj ETag не MD5).
* Если второй бакет недоступен — файл всё равно сохранён в первом, помечен
  `pending` и дозаписывается фоновой задачей. Загрузка для пользователя не падает.
* Миграция существующих файлов с диска в S3 — отдельный скрипт с отчётом.

### Шаг 2.2 — Фоновый воркер и бэкапы *(код)*
* Новый контейнер `worker` из того же образа: планировщик задач.
* Задачи: часовой бэкап, суточный бэкап, чистка часовых старше 7 дней,
  сверка бакетов (каждые 15 мин), снимок состояния кластера (каждые 30 сек),
  ночная проверка бэкапа восстановлением в чистую БД.
* Бэкап = `pg_dump` (сжатый) + манифест файлов; заливается в **оба** S3,
  рядом пишется SHA-256. Результат каждого прогона — в таблицу `backup_runs`.
* Суточные бэкапы кладём в отдельный префикс без правил автоудаления —
  их не трогает ни чистка, ни lifecycle-политика бакета.

### Шаг 2.3 — Страницы админки *(код)*
Вкладки «Кластер», «Бэкапы», «Хранилище» + расширение «Состояние системы»
и «Логов процессов» (см. таблицу выше).

### Шаг 2.4 — Репликация и переключение *(конфигурация + код)*
* PostgreSQL 16: потоковая репликация через слот, `synchronous_commit = on`
  (локальный fsync), `synchronous_standby_names = ''` — асинхронный режим,
  выбранный из-за расстояния между площадками. Плюс `wal_compression = on`
  (трафик идёт через границу) и `max_slot_wal_keep_size` — чтобы надолго
  отставший резерв не забил диск главного своими журналами.
* **Надзор за окном потери:** воркер каждые 30 секунд смотрит на отставание
  реплики и шлёт тревогу, когда оно превысило порог или реплика вовсе
  отвалилась. В синхронном режиме (если серверы однажды съедутся в один
  город) тот же сторож вместо этого спасает от блокировки записи: опускает
  режим до асинхронного, когда резерв умер, и поднимает обратно при возврате.
* Watchdog: резерв проверяет активный узел из двух точек (сам + внешняя
  проба). Только при обоих отрицательных ответах — переключение:
  забрать IP → повысить реплику до мастера → запустить фоновые задачи.
* Возврат на исходный сервер — управляемый, кнопкой, не автоматом
  (иначе получаем «пинг-понг» при мигающей сети).

### Шаг 3–7 — Серверы, деплой, проверка
Подготовка серверов, выкладка, подключение домена и TLS, учения:
гасим сервер A под нагрузкой и замеряем реальное время переключения и
потери запросов; восстанавливаем БД из суточного бэкапа в чистую среду.

## 4. Честные риски и оговорки

1. **Два узла — не кворум.** Классическая проблема: если сеть между
   серверами оборвалась, а оба живы, каждый может решить, что он главный
   («split-brain») — и данные разъедутся. Надёжное лечение — третий
   дешёвый микро-сервер-арбитр (только голосует, ничего не хранит,
   ~200–400 ₽/мес). **Настоятельно рекомендую его заложить.** Без арбитра
   переключение придётся страховать более грубым способом (fencing через
   API провайдера), это работает, но менее аккуратно.
2. **Асинхронная реплика ↔ потеря данных.** Размен сделан в пользу скорости:
   серверы стоят в Нидерландах и Финляндии (~30 мс), синхронный режим добавил
   бы эти 30 мс к каждой записи. Плата — при внезапной потере активного узла
   исчезает всё, что не успело доехать до резерва. Обычно это доли секунды
   работы, но гарантированного нуля, в отличие от синхронного режима, нет.
   Ограничитель ущерба — часовые бэкапы и тревога при росте отставания.
3. **«Точь-в-точь на каждом этапе» для S3** достигается двойной записью и
   регулярной сверкой по SHA-256, но между записью в первый и второй бакет
   всегда есть окно в доли секунды. Расхождение фиксируется и чинится
   автоматически; полностью нулевого окна на разных провайдерах не бывает.
4. **Ручные правки на проде.** Часть текущего прода правилась прямо на
   сервере и в git этого нет. Перед любой выкладкой снимаем с прода diff
   и переносим правки в репозиторий — иначе деплой их затрёт.
5. **Бэкап без проверки восстановлением — не бэкап.** Поэтому ночная
   задача реально разворачивает свежий дамп в чистую БД и сверяет ключевые
   счётчики. Именно её статус выводится в админке.

## 5. Что нужно от заказчика

1. **HostKey:** доступен ли дополнительный IP, переносимый между серверами
   (failover-IP / VRRP), и есть ли приватная сеть между машинами? От этого
   зависит, будет переключение за секунды или за минуты.
2. **Где обслуживается DNS домена cargo-ibragim.ru** (reg.ru, Cloudflare,
   …) и есть ли API-доступ — нужен для запасного варианта переключения.
3. **TLS:** имеющийся сертификат покрывает `flow.cargo-ibragim.ru`
   (wildcard `*.cargo-ibragim.ru`) или нужен отдельный?
4. **Реквизиты S3** обоих хранилищ (endpoint, бакет, ключи) — по мере
   покупки; код готовится заранее и включается конфигом.
5. Решение по третьему микро-серверу-арбитру (п. 4.1).
